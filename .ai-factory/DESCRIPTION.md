# ViaTrade Telegram Bot

## Обзор

ViaTrade Telegram Bot — отдельный асинхронный Python-сервис, который привязывает
Telegram-аккаунты пользователей ViaTrade и доставляет напоминания из Redis Stream.
Сервис обращается к внутреннему backend API по OpenAPI-контракту и подтверждает
доставку после успешной отправки сообщения в Telegram.

## Ключевые возможности

- Привязка Telegram-аккаунта по команде `/start <token>` через внутренний backend API.
- Чтение уведомлений из Redis Stream consumer group с блокирующим ожиданием и recovery
  необработанных сообщений.
- Дедупликация доставки, распределённая блокировка на уведомление и перенос некорректных
  либо окончательно отклонённых сообщений в dead-letter stream.
- Доставка напоминаний в Telegram и подтверждение доставки в backend API.
- Ограничение частоты сообщений из одного чата, безопасное логирование Telegram-апдейтов
  и централизованная обработка ошибок обработчиков.
- Генерация Python-клиента backend API из `swagger-tgbot.yaml`.

## Технологический стек

- **Язык:** Python 3.14.7+.
- **Сборка и зависимости:** `uv`, `uv_build`.
- **Telegram:** aiogram 3.
- **Redis:** `redis.asyncio`, Redis Streams и consumer groups.
- **HTTP и конфигурация:** httpx, pydantic, pydantic-settings.
- **Контракт backend API:** OpenAPI 3.0 и `openapi-python-client`.
- **База данных приложения:** не используется; Redis служит транспортом уведомлений и
  хранилищем состояния идемпотентности.
- **ORM:** не используется.

## Заметки по архитектуре

Сервис использует адаптированную слоистую архитектуру. `app.py` собирает зависимости и
управляет жизненным циклом. Пакет `bot/` содержит входной Telegram-слой, а
`notifications/` — обработку и оркестрацию доставки. Внешние системы изолированы в
адаптерах `integrations/`, `notifications/redis_client.py` и
`bot/notification_delivery.py`; связи между слоями задаются `Protocol`-контрактами и
внедряются через конструкторы.

## Нефункциональные требования

- **Надёжность:** корректно освобождать ресурсы при остановке, не подтверждать запись
  Redis Stream до подтверждения доставки backend API и повторно обрабатывать pending
  сообщения.
- **Обработка ошибок:** отделять ошибки некорректного сообщения и постоянные ошибки
  Telegram от временных ошибок внешних сервисов; первые направлять в DLQ, вторые
  логировать и оставлять доступными для повторной обработки.
- **Логирование:** применять стандартный `logging`, писать структурированные контекстные
  идентификаторы и не включать токены привязки или другие секреты.
- **Безопасность:** хранить `TELEGRAM_BOT_TOKEN` и пароль backend API только в окружении
  или защищённом хранилище; не добавлять реальные секреты в репозиторий.
- **Контракты:** поддерживать `swagger-tgbot.yaml` и
  `docs/notification-stream.asyncapi.yaml` как источники правды для HTTP- и
  Redis-сообщений.

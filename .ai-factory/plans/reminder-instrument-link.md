### 1. Пользовательский результат и границы

Новое напоминание приходит в личный Telegram-чат с прежним текстом и одной inline URL-кнопкой:

```text
Напоминание (AAPL):
Проверить условия входа после закрытия свечи.

[Открыть инструмент]
```

Кнопка открывает страницу именно того инструмента, к которому относится напоминание. Использовать стабильный числовой ID инструмента, а не тикер как идентификатор маршрута.

Для открытого браузера с действующей веб-сессией цель — соответствующая страница инструмента. Если пользователь не авторизован или приложение заблокировано PIN, работает существующая защита сайта. Бот не авторизует пользователя по ссылке и не обходит PIN. Сохранение адреса после входа зависит от существующего frontend routing и проверяется отдельно.

Ограничь задачу этой функцией. Не добавляй статистику, безопасность, новые меню, snooze, «Выполнено», создание напоминаний в чате, Telegram Mini App, отслеживание кликов или автоматическую торговлю. Не меняй смысл DeliveredAt: это подтверждение отправки сообщения, а не посещения страницы или выполнения задачи.

### 3. Решение, которое нужно реализовать

#### 3.1. Межсервисный контракт

Добавить `instrumentId` в JSON reminder payload. Бэкенд публикует корректный ID из существующей проекции напоминания, например из `reminder.Instrument.Id`, когда объект доступен. Не путать `reminderId`, `userId` и `instrumentId`; в тестах эти значения должны различаться.

Пример нового payload:

```json
{
  "reminderId": 42,
  "text": "Проверить инструмент",
  "remindAt": "2026-10-11T12:00:00Z",
  "instrumentTicker": "AAPL",
  "instrumentId": 123
}
```

В боте `instrumentId` — необязательный положительный int32 с default None. Значение null и отсутствие поля означают доставку без кнопки. Новое поле нужно валидировать как JSON integer: bool, строки и дробные числа не должны превращаться в корректный ID через неявное приведение типов.

Явно некорректное значение нового поля — invalid_payload по существующему механизму, аналогично другим неверным полям payload. Не меняй общую политику DLQ ради новой кнопки. При этом старый payload без поля не является ошибкой.

Сохранить существующий envelope, notification ID, тип `reminder`, имена Redis-полей и schemaVersion 1. Расширение аддитивное: старая версия бота должна игнорировать незнакомое поле, новая — принимать старые сообщения. Подтверди это по реальной модели и тестом, не полагайся только на предположение.

Публичный URL в Redis payload не передавать: backend отвечает за ID, бот — за построение ссылки и Telegram presentation. Текст напоминания и тикер не влияют на URL.

#### 3.2. Настройка адреса сайта

Добавить в настройки бота `VIATRADE_WEB_BASE_URL` / `viatrade_web_base_url`: необязательный публичный базовый URL сайта. Это одна настройка в боте; дублировать её на бэкенде не нужно.

Требования:

- Без настройки бот запускается и продолжает доставку прежних напоминаний без кнопки.
- Непустой некорректный URL вызывает понятную ошибку конфигурации при startup, до обработки очереди.
- Использовать абсолютный HTTP(S) URL. Для production рекомендовать HTTPS; HTTP допустим для локальной разработки.
- Не принимать userinfo (логин/пароль в URL), query и fragment в базовом адресе, а также javascript:, data:, tg: и protocol-relative адреса.
- Поддержать адрес с завершающим `/` и без него; при наличии префикса пути сохранять его: `https://example.test/viatrade/` → `https://example.test/viatrade/stocks/123`.
- Итоговый URL строить только из проверенной конфигурации, фиксированного пути `stocks/` и валидного числового instrumentId.
- Не использовать небезопасное URL-joining, которое незаметно отбрасывает префикс пути. Реализация должна быть небольшой; универсальный routing framework не нужен.
- Никогда не помещать в URL JWT, refresh token, сервисный пароль, Telegram link token, userId или текст напоминания.

Если можно выяснить реальный публичный origin из несекретной конфигурации или документации, используй подтверждённые сведения. Если нет, запроси у пользователя один раз публичный адрес сайта для настройки/ручной проверки и продолжай независимые изменения и тесты. Не подменяй неизвестный адрес выдуманным доменом или внутренним API. Не записывай новые значения в реальный .env без полученного адреса и явной необходимости; достаточно обновить .env.example и документацию.

#### 3.3. Граница application-логики и Telegram

Расширить контракт отправки минимальным способом, позволяющим передать необязательную ссылку для кнопки. Предпочтительно — keyword-only параметр `instrument_url: str | None = None` у существующего `send_text`; окончательное имя согласовать с окружающим кодом.

Не передавать aiogram InlineKeyboardMarkup из application-слоя и не импортировать aiogram в notifications/handlers.py или delivery.py ради этой функции. Конкретную клавиатуру строить в `bot/notification_delivery.py`.

ReminderNotificationHandler получает настройку/небольшой URL-builder через существующий DI, строит необязательную ссылку и передаёт её контракту доставки. Сохрани прежний текст сообщения и parse_mode=None для произвольного пользовательского текста. Новая строка URL в теле сообщения не нужна.

Если выделяешь helper, он должен решать конкретную задачу построения ссылки и иметь простую проверяемую функцию. Не создавай общий service registry, новый слой архитектуры или фабрику кнопок.

#### 3.4. Кнопка и длинные сообщения

Использовать InlineKeyboardMarkup с одной InlineKeyboardButton:

- label: `Открыть инструмент`;
- действие: URL, не callback_data и не web_app;
- URL: вычисленный адрес страницы инструмента.

Если сообщение разбито на части, кнопку прикреплять только к последней части. Не отправлять отдельное пустое сообщение с кнопкой и не повторять кнопку на каждом фрагменте. Если ссылки нет, отправлять без reply_markup.

Сохрани существующее разбиение текста и его содержимое, включая спецсимволы и переносы. Не меняй лимиты и алгоритм разбиения без необходимости; возможные существующие ограничения не выдавай за исправленные этой задачей.

URL-кнопка не создаёт callback update: обработчик клика, вызов backend при клике и новый HTTP endpoint не нужны. Не отмечать напоминание повторно доставленным после открытия ссылки.

#### 3.5. Надёжность

Сохранить порядок и условия существующей доставки:

```text
валидация → lock → проверка дедупликации → отправка всех частей
→ запись «отправлено в Telegram» → подтверждение backend → Redis ack
→ освобождение lock
```

Если конкретный порядок в актуальном коде отличается деталями, сохрани его инварианты и существующие тесты. Нельзя отмечать сообщение отправленным, подтверждать backend или делать ack до успешной отправки последней части вместе с кнопкой.

При ошибке подтверждения backend повторная обработка не должна повторно отправлять уже отмеченное отправленным сообщение. Ошибки и cancellation должны сохранять нынешнюю классификацию: invalid payload / permanent rejection → DLQ; временные ошибки → pending/retry; cancellation → propagation и освобождение ресурсов.

Не обещай exactly-once доставку: многосоставная отправка и сбой между Telegram и отметкой в Redis уже имеют ограничения. Не добавляй отдельный механизм идемпотентности фрагментов в эту задачу.

### 5. Минимальная матрица тестов

Проверки должны покрывать поведение, а не повторять устройство реализации.

**Backend и совместимость:**

1. Реальный publisher получает напоминание с reminderId=42, userId=7, instrumentId=123, ticker=AAPL; опубликованный payload содержит instrumentId=123, а остальные значения не перепутаны.
2. Сериализация сохраняет camelCase, тип `reminder`, прежний notification ID и шесть Redis-полей.
3. Payload, произведённый backend, принимается моделью бота. По возможности использовать настоящий результат C#-сериализации как вход проверки совместимости без ручной подмены значений.
4. Новая модель принимает старый payload без instrumentId и null. Существующий старый consumer игнорирует дополнительное поле: проверить на исходном модельном поведении до замены или отдельной совместимой фикстуре.
5. Новое поле не приводит к миграции БД, новому HTTP endpoint или изменению подтверждения доставки.

**Настройка и ссылки:**

6. Отсутствующая настройка → обычное сообщение без кнопки, успешные confirm/ack.
7. HTTPS origin с завершающим / и без него → одинаковый URL `/stocks/123`.
8. Base URL с префиксом пути → префикс сохранён.
9. Локальный HTTP URL с портом принимается; протокол вне HTTP(S), отсутствующий host, userinfo, query, fragment → ошибка настроек.
10. instrumentId missing/null → обычная доставка без кнопки. Положительный int32 → кнопка даже при отсутствии ticker.
11. instrumentId=0, отрицательный, за пределами int32, bool, строка, дробь → invalid_payload, без отправки/confirm; существующий механизм DLQ работает.
12. URL зависит только от конфигурации и ID; текст с HTML, &, ссылками или похожим на URL тикером не изменяет адрес кнопки и передаётся без HTML parsing.

**Telegram и consumer:**

13. Одна часть → ровно одна inline URL-кнопка с label «Открыть инструмент», ожидаемым URL, без callback_data/web_app.
14. Несколько частей → текст полностью сохранён, прежние ограничения частей соблюдены, клавиатура только у последней части.
15. Доставка без ссылки сохраняет прежнее поведение send_text и parse_mode=None.
16. Ошибка отправки последней части → нет mark_sent/confirm/ack; блокировка освобождена; transient/permanent errors сохраняют существующую классификацию.
17. После успешной отправки с кнопкой порядок mark_sent → backend confirm → ack сохранён.
18. Backend confirm временно падает после отправки → повторная обработка не отправляет сообщение и кнопку заново после существующей отметки дедупликации.
19. Cancellation не проглатывается; ресурсы освобождаются.
20. Dishka-контейнер создаёт обновлённый handler и delivery; существующие provider/lifecycle tests проходят.

**Ручные сценарии, если доступны внешние системы:**

21. Создать реальное напоминание для известного инструмента; получить сообщение и открыть соответствующий instrument ID по кнопке.
22. Проверить ссылку во внешнем браузере с авторизацией и без неё; отдельно — при включённом PIN. Не обходить существующую защиту. Если сайт после login теряет целевой путь, зафиксировать конкретный frontend-блокер.
23. Повторно обработать ту же запись; проверить отсутствие повторного сообщения в рамках существующей дедупликации.
24. Если инструмент недоступен/удалён, ссылка не даёт дополнительных прав: используется существующее поведение сайта/API. Не добавлять обход авторизации или auto-login.

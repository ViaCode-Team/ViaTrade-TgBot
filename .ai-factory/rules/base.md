# Базовые правила проекта

> Правила автоматически определены по текущему коду. Уточняйте их по мере развития проекта.

## Именование

- Файлы, модули, переменные и функции используют `snake_case`.
- Классы, Pydantic-модели и исключения используют `PascalCase`.
- Константы используют `UPPER_SNAKE_CASE`; публичные псевдонимы типов могут использовать
  `PascalCase`.
- Внутренние поля объектов и вспомогательные функции обозначаются префиксом `_`.

## Структура модулей

- Исходный код расположен в `src/` layout; корневой пакет — `src/viatradetgbot/`.
- `app.py` — composition root: он управляет жизненным циклом приложения; `providers.py`
  создаёт Redis-, HTTP- и Telegram-адаптеры в Dishka app-scope и финализирует ресурсы.
- `bot/` содержит aiogram-обработчики, middleware и Telegram-адаптеры. Обработчики
  зависят от контрактов, а не от конкретных HTTP-клиентов.
- `notifications/` содержит модели уведомлений, `Protocol`-контракты, consumer Redis
  Stream, обработчики типов уведомлений и Redis-адаптер.
- `integrations/` содержит адаптеры внешних HTTP-сервисов. Код в `backend_api/gen/`
  генерируется из OpenAPI и вручную не редактируется.

## Контракты и зависимости

- Границы внешних систем задавайте через `typing.Protocol`; конкретные реализации
  передавайте в конструктор.
- Направляйте зависимости от входных обработчиков к application-логике и контрактам, а
  к Redis, HTTP и Telegram — только через адаптеры.
- Не импортируйте `BackendApi` в Telegram-обработчики и не обращайтесь к Redis напрямую
  из них.
- При изменении HTTP- или stream-контракта сначала обновляйте
  `swagger-tgbot.yaml` либо `docs/notification-stream.asyncapi.yaml`; клиент backend API
  перегенерируйте командой `uv run generate-api`.

## Обработка ошибок

- Для известных ошибок используйте специализированные исключения и обрабатывайте их на
  соответствующей границе: ошибку схемы или постоянный отказ Telegram отправляйте в DLQ,
  временные ошибки Redis и HTTP логируйте с возможностью повторной попытки.
- Не перехватывайте `asyncio.CancelledError`: передавайте его дальше, чтобы остановка
  приложения оставалась корректной.
- Освобождайте ресурсы и блокировки в `finally`; для асинхронных ресурсов используйте
  контекстные менеджеры и явное закрытие.

## Поток управления

- Предпочитайте плоский и читаемый поток управления вместо глубокой вложенности.
- Используйте guard clauses и ранние `return` для нерелевантных событий, отсутствующих
  данных и постоянных ошибок.
- Основной путь обработки уведомления сохраняйте явным: валидация → блокировка →
  дедупликация → доставка → подтверждение backend API → `ack`.

## Логирование

- Получайте логгер через `logging.getLogger(__name__)` для модулей или по имени класса
  для сервисов.
- Логируйте контекстные идентификаторы (`update_id`, `chat_id`, `notification_id`,
  `message_id`) и передавайте stack trace через `logger.exception` либо `exc_info=True`.
- Не логируйте токен из `/start`, секреты конфигурации, содержимое авторизационных
  заголовков или другие чувствительные данные.

## Тестирование

- Используйте `unittest.IsolatedAsyncioTestCase` для асинхронных сценариев.
- Подменяйте Redis, доставку и backend API небольшими fake-реализациями контрактов,
  проверяя порядок вызовов и итоговые побочные эффекты.
- Покрывайте normal path, невалидные сообщения, постоянные ошибки доставки и повторную
  обработку уведомлений.

# ViaTrade Telegram Bot

Сервис привязывает Telegram-аккаунты ViaTrade и доставляет напоминания через
автогенерируемый клиент API из `swagger-tgbot.yaml`.

## Запуск

1. Скопируйте `.env.example` в `.env` и заполните секреты.
2. Выполните `uv sync`.
3. Запустите `uv run viatradetgbot`.

Для локального ASP.NET Core backend с самоподписанным HTTPS-сертификатом
экспортируйте публичный сертификат в PEM (PowerShell):

```powershell
New-Item -ItemType Directory -Path .certs -Force
dotnet dev-certs https --export-path "$PWD/.certs/backend-localhost.pem" --format PEM
```

Добавьте в `.env` строку `BACKEND_CA_BUNDLE=.certs/backend-localhost.pem`.
Проверка сертификата и имени сервера остаётся включённой. Без этой настройки
используется стандартное доверие HTTPX. Для собственного центра сертификации укажите
путь к его PEM bundle; отсутствующий или некорректный файл приводит к ошибке при запуске.
После замены сертификата backend повторите экспорт. Каталог `.certs/` исключён из Git.

Повторные сообщения из одного чата ограничиваются интервалом
`TELEGRAM_MESSAGE_RATE_LIMIT_SECONDS` (по умолчанию — 1 секунда).

Backend добавляет готовые к отправке напоминания в Redis Stream. Бот читает их через
Redis consumer group с блокирующим ожиданием новых записей, поэтому не выполняет
периодических запросов к backend. После успешной отправки в Telegram бот подтверждает
доставку через `PUT /api/v1/internal/tgbot/reminders/{reminderId}/delivery` и
подтверждает запись в Stream. Неподтверждённые сообщения возвращаются в обработку после
тайм-аута периодической задачей APScheduler, а сообщения с некорректным форматом
переносятся в `<NOTIFICATION_STREAM>:dead-letter`. Dishka создаёт зависимости уровня
приложения и внедряет контракт backend API прямо в aiogram-обработчик `/start`.

Формат сообщений определяет [AsyncAPI-контракт](docs/notification-stream.asyncapi.yaml):
backend публикует поля `notification_id`, `type`, `user_id`, `chat_id`, `payload`
и `created_at`, где `payload` — JSON. Этот формат без версии обрабатывается как
версия схемы 1. Также поддерживается единственное поле `message` с JSON уведомления
и явным `schemaVersion: 1`. Тикер инструмента передаётся в поле `instrumentTicker`.
Бот использует `chat_id` / `chatId` как идентификатор Telegram-чата;
`userId` передаётся backend при подтверждении доставки. Изменить API-клиент после
обновления HTTP-контракта можно командой `uv run generate-api`.

## Переход из напоминания к инструменту

Backend передаёт стабильный числовой `instrumentId` в JSON payload напоминания.
Метка «Напоминание» и тикер находятся в первой строке. Ниже курсивом выводится
запланированная дата и время, затем — текст, без пустых строк и смайликов.
Метка «Напоминание» и тикер выделены жирным, текст остаётся обычным.
Если задан `VIATRADE_WEB_BASE_URL`
и есть `instrumentId`, сам тикер становится ссылкой на `/stocks/{instrumentId}`.
При отсутствии тикера подпись ссылки — «Инструмент». Inline-кнопок нет.

Например, сообщение для AAPL выглядит так (в Telegram AAPL — кликабельная ссылка):

> **Напоминание**: **AAPL**<br>
> *Запланировано: 11.10.2026, 15:00 МСК*<br>
> Купить при цене ниже 100.

Дата берётся из `payload.remindAt`, а не из времени публикации или фактической
доставки. Бот отображает её в московском времени (UTC+3), с явной подписью «МСК»,
в формате `ДД.ММ.ГГГГ, ЧЧ:ММ`. Значения с offset переводятся в UTC+3; старые значения
без offset трактуются как UTC по соглашению backend. Сайт отправляет выбранное время
в UTC; исходный часовой пояс пользователя в контракте не хранится. Пользователи
в других часовых поясах увидят тот же момент времени в МСК.

Оформление передаётся через Telegram entities с UTF-16 offsets, без HTML parsing.
Символы `<`, `&`, пробелы и переносы внутри текста сохраняются буквально.
В тикере повторные пробельные символы заменяются одиночными пробелами,
чтобы подпись инструмента оставалась в строке заголовка.
Длинное сообщение может визуально переноситься в Telegram и делиться на фрагменты
по ограничению длины.
При разбиении сообщения entities переносятся на соответствующие фрагменты;
ссылка относится только к подписи инструмента. Превью ссылок в напоминании отключено.
Тикер и текст не участвуют в построении URL.

В `.env` укажите публичный адрес **сайта**, доступный из браузера пользователя.
`BACKEND_BASE_URL` — внутренний API и для этой ссылки не используется. Пример ниже
иллюстрирует формат адреса и префикс пути, а не действующий домен:

```dotenv
VIATRADE_WEB_BASE_URL=https://example.test/viatrade/
```

В этом примере инструмент 123 открывается по
`https://example.test/viatrade/stocks/123`. Завершающий `/` необязателен;
префикс пути сохраняется. Для production рекомендуется HTTPS. HTTP с портом допустим
для локальной разработки и проверки построения ссылки: `http://localhost:5173`.
Этот localhost-адрес подходит для локального браузера; на телефоне localhost
указывает на сам телефон. До появления доступного адреса можно оставить
`VIATRADE_WEB_BASE_URL` пустым.
При развёртывании под префиксом frontend router и hosting должны поддерживать этот путь.

Отсутствующее или пустое значение настройки отключает переход по тикеру: бот запускается и
доставляет оформленные напоминания. Непустой некорректный адрес вызывает ошибку настроек
до запуска consumer. Разрешены только абсолютные HTTP(S) URL с host без userinfo,
query и fragment. JWT, пароли и токены привязки в ссылку не добавляются.

`instrumentId` необязателен: старые сообщения без него или с `null` доставляются
без ссылки на инструмент, даже при настроенном сайте. Допустим только JSON integer от 1 до 2147483647;
bool, строки, дробные числа и значения вне диапазона направляются в DLQ как
`invalid_payload`. Расширение аддитивное: шесть Redis-полей и schemaVersion 1 сохранены,
старый бот игнорирует дополнительное поле. Порядок обновления: бот → backend → настройка
адреса сайта. Уже отправленные сообщения автоматически не редактируются.

Ссылка открывает обычную страницу сайта с существующими проверками авторизации и PIN.
Бот не авторизует по ссылке. В коде фронтенда защищённый маршрут сохраняет исходный
location для возврата после входа; фактический возврат требует проверки в браузере
с конкретным hosting. Открытие ссылки не вызывает callback и не меняет `DeliveredAt`:
это время отправки сообщения, а не посещения страницы или выполнения напоминания.

Все фрагменты должны успешно отправиться до отметки в Redis, подтверждения backend
и ack. Если Telegram явно отклоняет URL текстовой ссылки как некорректный, бот один раз
повторяет только отклонённый фрагмент без text_link, сохраняя текст и жирное оформление,
и пишет предупреждение без URL и текста напоминания. Успешная отправка подтверждается
обычным порядком; ошибка ссылки сама по себе не отправляет напоминание в DLQ.
Остальные ошибки Telegram и ошибки этой повторной отправки сохраняют прежнюю
классификацию. При сбое подтверждения повтор не отправляет уже отмеченное сообщение заново.
Ранее перенесённые в DLQ записи автоматически не возвращаются в очередь.
Сбой между отправкой Telegram и отметкой Redis либо частичная отправка сохраняют
существующий риск дублей; exactly-once доставка не гарантируется.

## Проверки

```powershell
uv run ruff check --fix
uv run ruff check
uv run pyright
uv run python -m unittest discover -s tests
```

`tests/fixtures/reminder-stream-entry.json` получен настоящими C# publisher и Redis-адаптером
в тесте `PublishesInstrumentIdAndPreservesStreamContract` бэкенда (без подключения к Redis).
Он проверяет принятие Stream-сообщения ботом и прежней моделью payload. Для повторной
проверки межсервисной совместимости выполните backend-тесты и скопируйте их результат
`Tests/bin/Debug/net10.0/reminder-stream-entry.json` в эту фикстуру, затем запустите Python-тесты.
Unit-тесты не подтверждают доступность сайта и переход из настоящего Telegram-чата.
